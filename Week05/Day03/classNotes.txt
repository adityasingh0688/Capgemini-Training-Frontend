# Part 7: Angular Route Guards - Protecting Your Routes
 
## Problem Statement - Route Protection & Navigation Control
 
Extend your Smart Shopping Cart application with **route guards** to control access to different sections, protect sensitive routes, prevent data loss, and pre-load data before navigation. Implement all major types of Angular route guards without using a full authentication backend (simulate authentication state).
 
---
 
You will implement **three critical guard types** that every Angular developer must master:
 
### 1. CanActivate Guard - "Can I Enter This Route?"
 
**Real-World Scenario**: Protect routes that require authentication or specific permissions.
 
**Your Challenge**: Implement guards to answer these questions:
- Can a guest user view the shopping cart? **NO** → Redirect to login
- Can a regular customer access admin panel? **NO** → Redirect to home with error
- Can a logged-in user view their orders? **YES** → Allow navigation
- Can anyone checkout with an empty cart? **NO** → Redirect to cart
 
**Guards to Create**:
1. **AuthGuard** - Verify user is logged in
2. **AdminGuard** - Verify user has admin role
3. **CartGuard** - Verify cart is not empty
4. **RoleGuard** - Verify user has required role (from route data)
 
### 2. CanActivateChild Guard - "Can I Enter These Child Routes?"
 
**Real-World Scenario**: Protect all child routes under a parent route with a single guard.
 
**Your Challenge**: Instead of applying guards to 10 child routes individually, apply ONE guard to the parent.
 
**Example Structure**:
```
/profile (Protected Parent)
  ├── /profile/overview (Auto-protected)
  ├── /profile/settings (Auto-protected)
  ├── /profile/orders (Auto-protected)
  └── /profile/wishlist (Auto-protected)
 
/admin (Protected Parent)
  ├── /admin/dashboard (Auto-protected)
  ├── /admin/products (Auto-protected)
  ├── /admin/orders (Auto-protected)
  └── /admin/users (Auto-protected)
```
 
**Guards to Create**:
1. **ChildRoutesGuard** - Protect all profile child routes
2. **AdminChildGuard** - Protect all admin child routes
 
**Key Learning**: Efficiency and DRY principle in route protection.
 
### 3. CanDeactivate Guard - "Can I Leave This Route?"
 
**Real-World Scenario**: Prevent users from accidentally losing unsaved work.
 
**Your Challenge**: Implement guards to prevent navigation away from:
- **Checkout form** with unsaved shipping information
- **Profile settings** with unsaved changes
- **Contact form** with partially filled message
- **Product review form** with typed but unsubmitted review
 
**Guards to Create**:
1. **UnsavedChangesGuard** - Generic guard for any component with unsaved data
2. **FormDirtyGuard** - Guard that checks Angular form dirty state
 
**User Experience Flow**:
```
User fills checkout form → Clicks browser back button
→ Guard detects unsaved changes
→ Shows confirmation: "You have unsaved changes. Leave anyway?"
→ User clicks Cancel → Stays on page
→ User clicks OK → Navigation proceeds
```
 
---
 
## Detailed Implementation Requirements
 
### Part A: CanActivate Guards (4 Guards)
 
#### Guard 1: AuthGuard
**Purpose**: Prevent unauthenticated users from accessing protected routes.
 
**Protected Routes**: `/cart`, `/checkout`, `/orders`, `/profile`
 
**Logic**:
```typescript
if (user is logged in) {
  return true; // Allow navigation
} else {
  save current URL; // For redirect after login
  redirect to /login;
  return false; // Block navigation
}
```
 
**Test Cases**:
1. Guest tries `/cart` → Redirected to `/login?returnUrl=/cart`
2. Logged-in user accesses `/cart` → Allowed
3. After successful login → User redirected to originally requested URL
 
---
 
#### Guard 2: AdminGuard
**Purpose**: Ensure only admin users can access admin panel.
 
**Protected Routes**: `/admin/*`
 
**Logic**:
```typescript
if (user is NOT logged in) {
  redirect to /login;
  return false;
}
if (user role === 'admin') {
  return true; // Allow navigation
} else {
  show error notification: "Admin access required";
  redirect to /home;
  return false;
}
```
 
**Test Cases**:
1. Guest tries `/admin` → Redirected to `/login`
2. Customer tries `/admin` → Error message + redirect to `/home`
3. Admin accesses `/admin` → Allowed
 
---
 
#### Guard 3: CartGuard
**Purpose**: Prevent checkout with empty cart.
 
**Protected Routes**: `/checkout`
 
**Logic**:
```typescript
if (cart has items) {
  return true; // Allow navigation to checkout
} else {
  show warning: "Your cart is empty";
  redirect to /cart;
  return false;
}
```
 
**Test Cases**:
1. User with empty cart clicks "Checkout" → Warning + redirected to `/cart`
2. User with items in cart clicks "Checkout" → Allowed to proceed
 
---
 
#### Guard 4: RoleGuard (Generic with Route Data)
**Purpose**: Flexible guard that checks for roles specified in route configuration.
 
**Usage in Routes**:
```typescript
{
  path: 'orders',
  component: OrderHistoryComponent,
  canActivate: [roleGuard],
  data: { roles: ['customer', 'admin'] } // <-- Roles defined here
}
```
 
**Logic**:
```typescript
const requiredRoles = route.data['roles']; // Read from route config
const userRole = authService.getUserRole();
 
if (requiredRoles.includes(userRole)) {
  return true;
} else {
  show error + redirect;
  return false;
}
```
 
**Test Cases**:
1. Guest tries route requiring 'customer' role → Blocked
2. Customer tries route requiring 'admin' role → Blocked
3. Admin tries route requiring 'customer' or 'admin' → Allowed
 
---
 
### Part B: CanActivateChild Guard (1 Guard)
 
#### Guard 5: ChildRoutesGuard
**Purpose**: Protect all children of a parent route with one guard.
 
**Route Configuration**:
```typescript
{
  path: 'profile',
  component: ProfileLayoutComponent,
  canActivateChild: [childRoutesGuard], // <-- Applied to parent
  children: [
    { path: '', component: ProfileOverviewComponent },     // Protected
    { path: 'settings', component: ProfileSettingsComponent }, // Protected
    { path: 'orders', component: ProfileOrdersComponent },    // Protected
    { path: 'wishlist', component: ProfileWishlistComponent }  // Protected
  ]
}
```
 
**Logic**:
```typescript
// This guard runs for EVERY child route navigation
if (user is logged in) {
  return true; // Allow access to any child
} else {
  redirect to /login;
  return false; // Block all children
}
```
 
**Why Use This?**:
- Apply ONE guard instead of repeating `canActivate: [authGuard]` on 4 child routes
- Cleaner, more maintainable code
- Enforces consistent protection across entire section
 
**Test Cases**:
1. Guest tries `/profile` → Blocked
2. Guest tries `/profile/settings` → Blocked
3. Guest tries `/profile/orders` → Blocked
4. Logged-in user tries any `/profile/*` route → Allowed
 
---
 
### Part C: CanDeactivate Guard (1 Guard + Interface)
 
#### Guard 6: UnsavedChangesGuard
**Purpose**: Prevent users from losing unsaved form data.
 
**Step 1: Create Interface**
```typescript
export interface CanComponentDeactivate {
  canDeactivate: () => boolean | Observable<boolean>;
}
```
 
**Step 2: Implement Guard**
```typescript
export const unsavedChangesGuard: CanDeactivateFn<CanComponentDeactivate> =
  (component) => {
    if (component.canDeactivate) {
      return component.canDeactivate(); // Ask component if it's safe to leave
    }
    return true; // No interface implemented, allow navigation
  };
```
 
**Step 3: Implement in Components**
 
**CheckoutComponent Example**:
```typescript
export class CheckoutComponent implements CanComponentDeactivate {
  hasUnsavedChanges = false; // Track form state
 
  @ViewChild('checkoutForm') form!: NgForm;
 
  onFormChange() {
    this.hasUnsavedChanges = true; // User modified form
  }
 
  canDeactivate(): boolean {
    if (this.hasUnsavedChanges) {
      return confirm('You have unsaved changes. Do you really want to leave?');
    }
    return true; // No changes, safe to navigate away
  }
 
  onSubmit() {
    // After successful form submission
    this.hasUnsavedChanges = false; // Clear flag
    this.orderService.createOrder(...);
    this.router.navigate(['/orders']);
  }
}
```
 
**Step 4: Apply to Routes**
```typescript
{
  path: 'checkout',
  component: CheckoutComponent,
  canActivate: [authGuard, cartGuard],
  canDeactivate: [unsavedChangesGuard] // <-- Applied here
}
```
 
**User Flow**:
1. User starts filling checkout form
2. `hasUnsavedChanges = true`
3. User clicks browser back button
4. Guard calls `component.canDeactivate()`
5. Confirmation dialog appears
6. User clicks "Cancel" → Stays on page
7. User clicks "OK" → Navigation proceeds
 
**Test Cases**:
1. User fills form but doesn't submit → Tries to navigate → Confirmation appears
2. User submits form successfully → Tries to navigate → No confirmation (form clean)
3. User doesn't touch form → Tries to navigate → No confirmation (no changes)
